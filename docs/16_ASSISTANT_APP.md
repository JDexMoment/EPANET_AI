# 16. Приложение-ассистент: скриншот + модель сети → объяснение, графики, отчёты

Выбранный заказчиком вариант: **отдельная локальная программа** (вариант A).
Пользователь перетаскивает скриншот AquaBit и файл модели (`.inp`, `.NET`, `.epanet`),
программа: ① объясняет, что на экране; ② достаёт из модели точные данные;
③ считает гидравлику; ④ строит графики и отчёты; ⑤ умеет всё это описывать словами.

**Ничего не выдумывается:** числа берутся из модели и расчёта, VLM отвечает за «прочитать
экран» и «объяснить по-человечески». Это ключевое архитектурное правило.

---

## 1. Полная схема программы

```
                 ┌──────────────────── ПОЛЬЗОВАТЕЛЬ ────────────────────┐
                 │  перетащил: скриншот.png   модель.inp/.NET/.epanet   │
                 │  вопрос: «что здесь происходит?» / «отчёт по трубе»  │
                 └───────────────────────┬──────────────────────────────┘
                                         ▼
   ┌─────────────────────────────────────────────────────────────────────────┐
   │  ① ЗРЕНИЕ (VLM, локально, 4-бит)                                        │
   │     экран → тип окна · видимый текст · ID объектов · числа · расходы    │
   └───────────────────────────────┬─────────────────────────────────────────┘
                                   │  «факты со скрина» (текст)
                                   ▼
   ┌─────────────────────────────────────────────────────────────────────────┐
   │  ② МОДЕЛЬ СЕТИ (src/model_io)                                           │
   │     .inp / .NET / .epanet  →  параметры объекта, соседи, правила,       │
   │     паттерны, кастомные секции AquaBit                                  │
   └───────────────────────────────┬─────────────────────────────────────────┘
                                   │
                                   ▼
   ┌─────────────────────────────────────────────────────────────────────────┐
   │  ③ РАСЧЁТ И ГРАФИКИ (детерминированно, без ИИ)                          │
   │     V(Q), удельные потери i, полные h, режим (заиливание/норма/высокие) │
   │     зоны и трасса, баланс, графики matplotlib/plotly, шаблоны отчётов   │
   └───────────────────────────────┬─────────────────────────────────────────┘
                                   │  «факты + графики» (структура)
                                   ▼
   ┌─────────────────────────────────────────────────────────────────────────┐
   │  ④ ЯЗЫК (та же VLM, текстом)  — объясняет, отвечает, описывает график   │
   │     + ⑤ ИНТЕНТ: «сделай отчёт по…», «сравни…» → команды для ②③         │
   └───────────────────────────────┬─────────────────────────────────────────┘
                                   ▼
        КАРТОЧКА ОБЪЕКТА · ГРАФИКИ · ОТЧЁТ (экран/HTML/PDF/XLSX) · ИСТОРИЯ
```

### Почему именно так
* VLM **не считает** гидравлику и не помнит числа — она читает пиксели и пишет текст.
  Любая арифметика — в модуле ③, поэтому «галлюцинации в числах» структурно невозможны.
* Модель сети даёт «истину»: диаметр, длину, шероховатость, правила, спросы.
* Отчёты — это **программа**, а не знания модели: шаблон + данные + подпись словами.

## 2. Нужна ли CV-модель? — Да, но одна и уже есть в плане

| Задача | Кто решает |
|---|---|
| понять, что на экране (тип окна, объект, числа, тема раскраски) | **VLM** (Qwen3-VL + LoRA) — то же обучение, что и раньше |
| найти ID объектов и числа в видимом тексте | регулярки + словари (уже работают: `tools/extract_claims.py`) |
| отличить карту от свойств объекта, распознать кнопки/вкладки | VLM (классификация кадра) + подсказки из метаданных |
| точные параметры и расчёты | не CV: `src/model_io` + формулы (Хазен–Вильямс) |

То есть **отдельная CV-модель не нужна** (это позиция из `docs/12`, §1, она не изменилась):
роль «зрения» исполняет VLM. Отличие нового понимания — VLM теперь не единственный источник
данных: рядом работает модуль модели сети, который «видит» больше, чем любой скриншот (весь
граф из 21 тыс. узлов), и именно он отвечает за числа.

## 3. Три сценария работы (что увидит пользователь)

**Сценарий «что здесь происходит».** Перетащил скриншот + модель → ассистент:
«На экране свойства трубы 3459843 (Ø500, 218.96 м, статус открыта). При расходе 87.9 м³/ч
скорость 0.12 м/с — это зона заиливания; к 14:37 расход упал до 65.4 м³/ч, скорость 0.09 м/с.
Удельные потери 0.11 м/км. Участок лежит в магистральном водоводе, рядом насосы и резервуар…»

**Сценарий «сделай отчёт/график».** «Построй отчёт по трубам Ø500 и график V(Q) для 3459843» →
интент-разбор → запрос к модели → расчёт → график (картинка в окне) → текстовое описание
графика и вывод («диаметр достаточный, но режим застойный — риск заиливания») → экспорт
в HTML/PDF/XLSX.

**Сценарий «объект из модели».** Пишем/говорим «покажи узел 3382180» — карточка узла:
отметка 202.2 м, спрос по группам, соседние участки, правила, где он на карте (координаты уже
в `.inp` — можно нарисовать схему окрестности).

## 4. Что уже готово (можно показать заказчику сегодня)

`tools/assistant_prototype.py` — **работающий прототип без нейросети**: берёт модель и текст
со скриншота (или ID/расход напрямую), выдаёт:

* `card.html` — карточка объекта: параметры, расчёт, график V(Q) с отметками режима,
  правила управления, соседи, кастомная секция `[PRESS]` (если объект там упомянут);
* `context_for_vlm.txt` — «факты» для языковой части: только их модель имеет право пересказывать;
* `facts.json` — машинный вид (для GUI).

Демонстрация на реальных данных:

```powershell
python tools\assistant_prototype.py --model "модель для ИИ — копия.txt" `
       --screen "ответ_Gemini_к_слайду_09.txt" --out semey\work\assistant_demo
```

Проверено на модели Семей: труба 3459843 → V = 0.124/0.093 м/с при 87.9/65.4 м³/ч,
режим «заиливание» (в согласии с числами Gemini и с нашим разбором в `docs/13`).

**Что это доказывает:** связка «экран → модель → расчёт → график → текст» работает на реальных
данных уже сейчас; не хватает только приложения (GUI), VLM-части и шаблонов отчётов.

## 5. План разработки приложения

| Этап | Что делаем | Результат |
|---|---|---|
| **MVP-0** | прототип карточки (сделан) | демо заказчику, согласование вида карточки и отчётов |
| **MVP-1** | GUI: окно с drag&drop, выбор модели, кнопка «Объяснить»; запуск `llama-server` с VLM; показ карточки | приложение, работающее офлайн на ПК |
| **MVP-2** | интент-разбор запросов («что происходит», «отчёт по…», «сравни…») + 3–5 шаблонов отчётов и графиков + экспорт HTML/PDF/XLSX | «кастомные отчёты по запросу» в минимальном виде |
| **MVP-3** | обучаем VLM на большом датасете (экран → контекст), подключаем «видимый текст» как обязательное поле, приёмка по метрикам | качественные объяснения на любых экранах |
| **Дальше** | сравнение сценариев/моделей, история, зоны, трассы, подсказки «что если» (изменение диаметра и т.п.) | инженерный помощник целиком |

Техническая основа: Python + GUI (tkinter/PySide), `matplotlib`/`plotly` для графиков,
`llama.cpp` для VLM, наш `src/model_io` для моделей, `tools/assistant_prototype.py` как ядро карточки.

## 6. Ответ на главный вопрос: «достаточно ли просто увеличить количество информации в тех же форматах?»

Разделим два разных «сколько данных»:

### А. Чтобы VLM уверенно читала экраны — да, почти достаточно
Работает простое масштабирование: **больше скриншотов + ответов в тех же форматах**
(разные окна, проекты, режимы; PNG без сжатия). Порог полезности — от ~300–500 пар, комфорт —
1000+. Это чистое «количество → качество».

**Но два дополнения дадут непропорционально большой эффект:**
1. **`screen_text`** — текст, видимый на экране (OCR или вычитка). Это «шпаргалка» для VLM
   и одновременно будущий детектор выдуманных чисел. Формат тот же (одна колонка в таблице пар).
2. **Разные типы вопросов** в датасете, не только «проанализируй картинку»: «почему упало
   давление», «дай отчёт по…», «сравни с ночным режимом». Тогда модель научится и отвечать,
   и распознавать запросы.

### Б. Чтобы программа строила отчёты и графики — «информация в тех же форматах» НЕ нужна
Отчёты — это **код и шаблоны**, а не память модели:
* данные для отчёта берутся из модели `.inp/.NET/.epanet` и из выгрузок AquaBit;
* арифметика детерминированная (Хазен–Вильямс, зоны, балансы);
* график рисует `matplotlib`, а не модель;
* модель лишь **описывает** готовый график и **понимает формулировку** запроса.

Поэтому здесь рост качества идёт не от объёма датасета, а от **числа шаблонов отчётов**
и точности интент-разбора. В датасет имеет смысл добавлять образцы формулировок и структуры
отчётов (5–20 примеров достаточно), а не тысячи картинок.

### Итоговая формула качества
```
качество ответа = (VLM: экран → факты)  ×  (модель: факты/расчёты)  ×  (шаблоны: отчёты)
                   └── растёт от количества пар ──┘   └── растёт от кода, не от данных ──┘
```
То есть: **да, увеличивайте информацию в тех же форматах** — но приоритет отдавайте скриншотам
разных типов окон и проектов + колонке `screen_text`; отчёты и графики достижимы без роста датасета.

## 7. Требования к машине (локально, офлайн)

| Компонент | Требование | Комментарий |
|---|---|---|
| VLM (Qwen3-VL-4B, Q4) | ~2.5–3.5 ГБ ОЗУ + mmproj 0.8 ГБ | работает на CPU; GPU ускоряет |
| модель сети (21 тыс. узлов) | ~0.3–0.6 ГБ | индекс объектов строится за секунды |
| графики/отчёты | 0.2–0.5 ГБ | `matplotlib`, без ИИ |
| диск | папка приложения + модели ≈ 5 ГБ | полностью автономно |

## 8. Риски и рамки (честно)

1. **Динамика.** Ванильный расчёт не воспроизводит AquaBit (кастомные опции; см. `docs/13`, §4).
   Графики «V(Q)», статика, сравнение сценариев модели — можно всегда; графики «по времени»
   (расход за сутки) — только из выгрузок AquaBit. Запрос вендору уже сформулирован (`docs/15`, §3.3).
2. **Разнообразие экранов.** Пока модель видела один проект и один стиль кадров — сначала
   качество будет высоким «по Семею». Лечится только датасетом (этап MVP-3).
3. **Ожидания «она всё понимает».** В карточку и отчёт всегда кладём пометку, какие числа
   посчитаны по модели, а какие прочитаны с экрана. Это защищает от неверных решений.
4. **Юридически** — всё считается и обучается локально; наружу ничего не уходит.
