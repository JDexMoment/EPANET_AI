# Бенчмарк и контроль качества модели

## 1. Метрики (roadmap п.12) и пороги допуска

| Метрика | Что считает | Инструмент | Порог допуска |
|---|---|---|---|
| Fact accuracy | доля чисел в ответе, подтверждённых evidence/контекстом | `metrics_model.py` | ≥ 0,95 |
| Hallucination rate | 1 − fact accuracy (неподтверждённые числовые утверждения) | `metrics_model.py` | ≤ 0,05 |
| Citation rate | доля числовых утверждений со ссылкой `E-xxx` | `metrics_model.py` | ≥ 0,90 |
| Problem detection recall/precision | верно ли найдены проблемы и их носители | `metrics_model.py` (по `label` кейсов) | recall ≥ 0,90, precision ≥ 0,85 |
| Explanation quality | оценка инженерами (1–5) | ручная выборка 30–50 ответов | средняя ≥ 4,0 |
| Report completeness | наличие 6 обязательных разделов | `metrics_model.py` | ≥ 0,8 |
| Latency | p95 времени ответа | `metrics_model.py` | ≤ 8 с (контекст ≤ 12 000 символов) |
| VRAM/RAM | пиковое потребление | замер на месте внедрения | по конфигурации ПК |
| Throughput | запросов/мин | `metrics_model.py` | по нагрузке |

Дополнительно: **refusal correctness** — доля корректных «данных недостаточно» там, где
ответ невозможен (защита от уверенной болтовни). Цель ≥ 0,8.

## 2. Как собрать результаты для бенчмарка

1. Запустить модель на тест-наборе `data/splits/eval_test.jsonl` (инференс-скрипт работает
   с тем же `llm_context`, что видит инженер).
2. Сохранить журнал построчно:
   ```json
   {"case_id": "c_vn01__…__make_report__05", "answer": "…", "latency_s": 3.1,
    "prompt_tokens": 2400, "completion_tokens": 260, "vram_mb": 6200, "run": "qwen3.5-9b-lora-v1"}
   ```
   → `data/eval/predictions.jsonl`
3. Прогнать метрики:
   ```bash
   python -m src.eval.metrics_model --pred data/eval/predictions.jsonl \
     --eval-set data/splits/eval_test.jsonl --out data/eval/model_scores.json
   ```
4. Демонстрационный прогон (уже в репозитории): `data/eval/predictions.example.jsonl` →
   `data/eval/model_scores.example.json`.

## 3. Сравнение кандидатов

Обязательный эксперимент перед выбором модели (проводится на одном и том же тест-наборе):

| Кандидат | Режим | Что сравнить |
|---|---|---|
| Qwen3.5-9B | Q4, prompt-only (наш system prompt + контекст) | базовая линия: что модель умеет без обучения |
| **Qwen3.5-9B** | +LoRA на нашем датасете | **основной кандидат проекта** |
| Qwen3.5-4B | +LoRA | резерв для слабых ПК: насколько падает качество |
| Qwen3.5-35B-A3B | +LoRA | верхняя планка качества для машин «чуть мощнее» |

Правило приёмки MVP: **Qwen3.5-9B+LoRA должен обойти Qwen3.5-9B prompt-only** минимум по трём
метрикам, не ухудшив fact accuracy и hallucination rate. Затем фиксируем, какой из резервных
вариантов брать для клиентов с 8 ГБ RAM.

## 4. Контроль качества ДАННЫХ (не модели)

| Метрика | Инструмент | Цель |
|---|---|---|
| Валидные кейсы | `validate_cases.py` | 100 % без ошибок |
| Согласие по категории (IQA) | `check_quality.py` | ≥ 0,70 |
| Согласие по severity | `check_quality.py` | ≥ 0,65 |
| Пересечение evidence-ссылок | `check_quality.py` | ≥ 0,5 (Jaccard) |
| Доля «нет проблемы» / «данных недостаточно» | `metrics_offline.py` | 10–25 % |
| Баланс категорий | `metrics_offline.py` | ни одна категория не > 30 % |
| Доля сценариев со слабым эффектом | `metrics_offline.py` | ≤ 25 % |

## 5. Регрессионный набор (защита от деградации)

Собирается один раз и не меняется при дообучении:

1. 40–60 «золотых» кейсов из тест-сплита (все режимы, все категории).
2. 10–15 «ловушек»:
   - расчёт, где всё в норме (модель не должна найти аварию);
   - сценарий со слабым изменением (правильный ответ — «влияния нет / недостаточно данных»);
   - расчёт с предупреждениями решателя (модель должна их отметить);
   - вопрос про объект, которого нет в контексте (модель должна отказаться).
3. Прогон после каждого изменения промпта, контекст-билдера или адаптера.
4. Отчёт сравнения с предыдущим: `data/eval/regression_<дата>.json`.

## 6. Ручная оценка инженерами

- Слепая выборка 30–50 ответов модели, случайный порядок, без указания версии модели.
- Шкала: корректность фактов (1–5), корректность причин (1–5), полезность (1–5),
  честность в ограничениях (0/1).
- Расхождения в 2+ балла между экспертами — разбор на общей встрече; спорные формулировки
  уходят в правила system prompt, а не «в модель».

## 7. Что считается блокером выпуска

- любая выдуманная цифра в регрессионном наборе (fact accuracy < 0,95);
- предупреждения решателя не отражены в ответе;
- модель выдаёт причину как доказанный факт;
- отчёт без раздела «Ограничения»;
- ответ содержит объекты, которых нет в контексте.
