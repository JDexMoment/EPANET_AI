# Сервис сбора данных от инженеров (сайт разметки)

Этот сервис превращает разметку из «мы рассылаем формы» в «инженеры сами приносят свои сети»:
гидравлик заходит на сайт, загружает модель в любом формате, отмечает проблему или пишет
эталонный отчёт — и данные уезжают в датасет обучения **без участия владельца проекта**.

```
инженер → сайт (service/) → конвертация .inp/.NET/.epanet (EPANET-Model-Cleaner)
        → расчёт суток EPANET (PDA) → Analytics: KPI, алерты, факты E-xxx
        → инженер пишет разметку (самопроверка чисел и ссылок на месте)
        → SQLite + файлы на сервере → автоэкспорт каждые N часов → архив
        → python tools/pull_collected.py → data/collected/ → data/splits/ (датасет обучения)
```

## 1. Что умеет

| Возможность | Как сделано |
|---|---|
| Принимает **любой формат** модели | вендорные ETL-модули вашего [EPANET-Model-Cleaner](https://github.com/JDexMoment/EPANET-Model-Cleaner) (MIT): нативный бинарный `.NET`, zip-`.epanet`, `.inp` (в т.ч. cp1251) |
| Чистит модель | удаление BACKDROP/TAGS/LABELS, комментариев, пустых строк; отчёт «сколько строк удалено» |
| Считает расчёт | тот же пайплайн, что у датасета: `run_scenarios.run_one` → `analytics.build_derived` → `context_builder` |
| Показывает инженеру те же факты, что увидит модель | KPI, алерты Top-N, объекты, факты E-xxx, кнопка «Контекст модели (JSON)» |
| Три типа разметки | **проблема в элементе**, **эталонный отчёт**, **вопрос — эталонный ответ** (любые темы и запросы) |
| Самопроверка на месте | числа не из расчёта, ссылки на несуществующие факты, длина, отсутствие ссылок — красным прямо в форме |
| Не теряет работу | черновики в браузере, каждое сохранение пишется сразу на сервер |
| Автономность | `restart: always`, автоэкспорт по расписанию, ежедневный бэкап, автозапуск после перезагрузки сервера |
| Выгрузка в датасет | `/api/admin/export` → zip с кейсами в формате `schemas/case.schema.json` |
| Только реальные данные | в датасет идут модели и ответы инженеров; синтетика в `data/` не хранится (см. `data/README.md`) |

## 2. Как это выглядит для инженера

1. Открывает адрес, вводит токен (одно поле, без паролей — токен выдаёте вы).
2. Перетаскивает файл модели → через несколько секунд видит: сколько узлов и участков,
   что удалено при очистке, KPI расчёта, алерты, таблицу объектов.
3. Кликает по объекту (или по алерту) → в поле подставляется ID и подсказка с фактом.
4. Выбирает тип ответа, пишет наблюдения/причину/проверки/рекомендации/ограничения и итоговый текст.
5. Нажимает «Проверить ответ» — сразу видит, какие числа не подтверждены расчётом.
6. «Сохранить в датасет» → запись уходит на сервер. Внизу — счётчик своих разметок.

Ничего не нужно устанавливать, ничего не отправляется в интернет (шрифты и стили встроены,
никаких внешних CDN).

> Практика: как запустить, проверить и выдать ссылку инженеру — `docs/11_LAUNCH_AND_INVITE.md`.

## 3. Разворачивание на сервере (10 минут)

Нужен любой VPS (Ubuntu 22.04/24.04, 2 ГБ RAM, 1 vCPU — достаточно; `wntr` считает
демо-сеть за секунды, сети на несколько тысяч узлов — секунды-минуты).

```bash
# 1. скопировать проект на сервер (git clone или scp), затем:
cd /path/to/epanet-ai
bash deploy/install_vps.sh epanet.example.com     # домен необязателен
```

Скрипт: ставит docker, включает файрвол (22/80/443), копирует проект в `/opt/epanet-ai`,
генерирует `deploy/service.env` со случайными токенами, поднимает контейнеры
(app + Caddy с автоматическим TLS), включает автозапуск и ежедневный бэкап,
печатает адрес, токен админа и токены инженеров.

Без домена: `bash deploy/install_vps.sh` → сайт на `http://IP`.
С доменом Caddy сам получит сертификат Let's Encrypt.

Обновление версии:

```bash
cd /opt/epanet-ai && git pull && cd deploy && docker compose --env-file service.env up -d --build
```

## 4. Автономная работа («даже когда мой ноут выключен»)

| Механизм | Настройка | Что даёт |
|---|---|---|
| `restart: always` в compose | по умолчанию | сервис поднимается после падений и перезагрузок |
| systemd-юнит `epanet-ai.service` | ставит `install_vps.sh` | запуск контейнеров при старте сервера |
| авто-экспорт | `AUTO_EXPORT_HOURS=6` | архив `collected_auto_*.zip` каждые 6 часов в `service_data/exports/` |
| хранение архивов | `KEEP_EXPORTS=30` | не растёт бесконечно |
| внешняя копия | `BACKUP_CMD=rclone copy {file} yandex:epanet-ai` | данные уезжают в облако вне сервера |
| уведомление | `ANNOUNCE_WEBHOOK=<telegram bot url>` | сообщение «собрано N кейсов» |
| ежедневный бэкап | cron 03:30 (`deploy/backup.sh`) | tar.gz с БД и всеми моделями, ротация 14 штук |
| healthcheck | `/health` | docker перезапустит контейнер, если сервис завис |

Проверка, что всё живо: `curl https://ваш-домен/health` → `{"status":"ok", ...}`.

## 5. Как забрать данные себе

```bash
# на своём компьютере
python tools/pull_collected.py --url https://epanet.example.com --token <ADMIN_TOKEN> --pipeline
```

Что произойдёт: скачается `latest.zip`, распакуется в `data/collected/`
(`cases/*.json`, `models/*/network_clean.inp`, `annotations_raw.jsonl`, `manifest.json`),
затем прогонится конвейер: `validate_cases` → `check_quality` → `export_instruct`
→ `metrics_offline`. На выходе — `data/splits_collected/{train,val,test,structured,eval_test}.jsonl`.

Без `--pipeline` просто распакует; можно и вручную:

```bash
python -m src.dataset.validate_cases --dir data/collected/cases
python -m src.dataset.check_quality  --dir data/collected/cases
python -m src.dataset.export_instruct --dir data/collected/cases --out data/splits_collected
```

Кейсы из сервиса получают `annotation.review_status = "submitted"` и поле
`annotation.source = "collection_service"`, поэтому их легко отличить от разметки по
внутренним сценариям и при желании требовать ревью ведущего инженера (флаг
`--include-candidates` в `export_instruct` оставлен для будущего статуса `candidate`).

## 6. Админка

`https://ваш-домен/admin` (вход по `ADMIN_TOKEN`):

* сводка: модели, разметки, новые (не выгруженные), эксперты;
* кнопки выгрузки: «собрать архив (только новые / всё)», «скачать latest.zip»,
  «скачать полный бэкап (БД + модели)»;
* создание доступа для нового инженера: имя + роль → выдаёт токен (передайте лично);
* таблицы моделей (кто загрузил, статус), разметок (со результатом самопроверки)
  и журнал событий (вход, загрузки, сохранения, экспорты, ошибки).

## 7. Безопасность и приватность

* Модель не публикуется: файлы лежат в `service_data/`, доступ только по токену эксперта/админа.
* Инженер не видит чужие разметки; админ видит всё.
* Пределы против абьюза: размер файла (`MAX_UPLOAD_MB`), частота загрузок
  (`MAX_UPLOADS_PER_DAY`), частота разметок (`MAX_ANNOTATIONS_PER_HOUR`).
* Никаких внешних запросов из браузера: страницы самодостаточные (0 внешних URL).
* Дедупликация по SHA-256: повторная загрузка той же модели не создаёт дубль.
* Рекомендуется: отдельный домен, токены не в мессенджерах, `chmod 600 deploy/service.env`,
  HTTPS (Caddy делает автоматически).

## 9. Структура кода

```
service/
  app.py          # HTTP-API и маршруты (FastAPI)
  config.py       # настройки из переменных окружения
  storage.py      # SQLite: модели, аннотации, эксперты, события
  conversion.py   # любой формат → чистый .inp (вендор EPANET-Model-Cleaner)
  modeling.py     # расчёт EPANET + аналитика + контексты для LLM
  quality.py      # самопроверка ответа инженера
  export.py       # кейсы датасета, архивы, автоэкспорт, внешние бэкапы
  static/index.html   # интерфейс инженера
  static/admin.html   # админка
  vendor/emc/     # копия ETL-модулей клинера (MIT), без GUI
deploy/
  Dockerfile · docker-compose.yml · Caddyfile · service.env.example
  install_vps.sh  # установка на чистый VPS одной командой
  backup.sh       # ежедневный бэкап + копия наружу
tools/pull_collected.py  # забрать собранное и превратить в датасет
```

## 10. Что дальше можно добавить (когда будет спрос)

* **Сравнение двух версий одной сети**: инженер загружает модель дважды (до/после мероприятия) —
  сервис считает `compare_scenarios` и даёт кейс «что изменилось».
* **Ревью ведущим инженером** прямо в админке (сейчас только экспорт со статусом `submitted`).
* **Telegram-бот**: та же разметка из чата (API уже даёт всё нужное).
* **Онлайн-очередь**: если моделей станет много, расчёт вынести в отдельный воркер (сейчас расчёт
  синхронный, для сетей до ~10 тыс. узлов это секунды).
* **Автоматическое наполнение «ловушек»**: сервис может сам подмешивать в интерфейс заведомо
  нормальную сеть и проверять, не находит ли инженер несуществующую проблему.
