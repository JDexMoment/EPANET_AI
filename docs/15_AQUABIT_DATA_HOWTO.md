# 15. Как собирать данные: таблица пар, экспорт из AquaBit, отчёты

Практическое руководство под текущие возможности (только скриншоты + ответы Gemini;
больше моделей и отчётов; без эталонов инженеров). Ссылки на страницы — по руководству
пользователя AquaBit v.2 (05.02.2021).

---

## 1. «Нам нужны только скриншоты?» — короткий ответ

**Для обучения модели — да, пары «скриншот + ответ».** Но `.inp` и отчёты нужны, только
для другой работы — они **не учат модель**, а **проверяют её и эталон**:

| Материал | Нужен? | Для чего именно |
|---|---|---|
| скриншоты + ответы Gemini | **да, главное** | обучающие пары (эталон ответа) |
| `.inp` проекта | **очень желательно** | проверка чисел из ответов Gemini по модели; позже — автопроверка ответов готовой модели |
| результаты расчёта (Q, P во времени) | **желательно** | истина по «динамике»: подтвердить или опровергнуть утверждения про падение расхода и т.п. |
| отчёты (PDF) | полезно | справочник терминологии и нормативов; таблицы для сверки; картинки — отдельный материал |

Что это даёт на практике (уже проверено на присланных 24 парах): инструмент
`tools/extract_claims.py` вытащил из ответов Gemini **43 утверждения** и сверил с моделью:
**28 подтвердились** (24 «точно», 4 — с уточнением единиц), **2 расхождения**, 13 нечем
проверить без расчёта. Без `.inp` мы бы вообще не знали, где Gemini прав.

## 2. Как сделать таблицу пар (ваши 300+ скриншотов)

### Способ 1 — «папки и одинаковые имена» (самый простой)
1. Все скриншоты — в одну папку, имена любые (`001.png`, `диаметр-центр.png`, …).
2. Запустить утилиту-заготовку:
   ```
   python tools/prepare_pairs_worksheet.py --shots D:\Семей\скрины --out D:\Семей\датасет
   ```
   Она создаст `D:\Семей\датасет\answers\001.txt` … под каждый скриншот и таблицу `pairs.csv`.
3. Открыть скриншот, задать Gemini вопрос, **скопировать ответ целиком** в соответствующий
   `.txt`. Один скриншот = один ответ = один файл.
4. Повторный запуск утилиты безопасен: заполненные ответы не затираются, новые скриншоты
   добавляются. Так можно набирать датасет порциями.

### Способ 2 — «одна таблица» (когда удобнее CSV/Excel)
Заполнять `pairs.csv` (шаблон — `data/screens/pairs_template.csv`); минимально нужны
`image`, `question`, `answer`, остальные колонки приветствуются:

| колонка | обязательна | что писать |
|---|---|---|
| `image` | **да** | имя файла картинки |
| `question` | **да** | вопрос, который задавали Gemini (у нас единый: «Проанализируй картинку.») |
| `answer` | **да** | полный текст ответа (без обрезки, можно с переносами — берите в кавычки) |
| `session` / `project` | желательно | какой проект/модель (чтобы сплиты резались по проектам) |
| `window_type` | желательно | что за окно: карта/тема, свойства трубы, отчёт, график, журнал расчёта… |
| `result_time` | желательно | момент на «регуляторе времени», если виден |
| `screen_text` | по возможности | текст, видимый на экране (OCR или руками) — им ловим выдуманные числа |
| `notes` | свободно | ваши пометки |

### Проверка и приём (одна команда)
```powershell
python -m src.dataset.import_screenshots --src D:\Семей\датасет --summary
python -m src.dataset.check_screenshot_pairs --manifest D:\Семей\датасет\manifest.jsonl
python -m src.dataset.build_vl_dataset   --manifest D:\Семей\датасет\manifest.jsonl --out D:\Семей\датасет\vl
```
Контроль качества сам скажет: сколько пар сшилось, сколько дубликатов кадров, нет ли
блокирующих проблем, как поделились train/val/test.

### Важные мелочи, которые потом дорого стоят
* **вопрос один и тот же** для всех кадров (иначе модель запутается в формате ответа);
* **ответ копировать целиком**, включая список и выводы — обрезанный ответ учит обрывать ответы;
* **не переименовывать** скриншоты после разговора с Gemini (иначе потеряется связь);
* **PNG без пережатия** (не через мессенджер), ширина ≥ 1600 px, полное окно программы.

## 3. Как экспортировать результаты расчёта из AquaBit

### 3.1. Что об этом есть в руководстве

| Команда | Где | Стр. руководства |
|---|---|---|
| Расчёт модели (кнопка «Расчет») | подменю «Расчет» / главное меню | 37, 81 |
| «Журнал расчета» (ошибки/предупреждения расчёта) | появляется вкладкой после расчёта | 81 |
| **Регулятор времени** (ползунок по датам/часам) | после расчёта; двигает момент для графиков и отчётов | 82 |
| **Отчёты по объекту**: выделить объект → поставить время → **двойной клик по серому полю** в свойствах → выбрать поля → ОК | редактор свойств объекта | 82–84 |
| **Отчёты по модели**: меню «Отчёты» → сводный / по трубам / по профилю / электроэнергия / калибровки / СКО / баланс / оплата по зонам / сравнение моделей | главное меню | 84–88 |
| Утилита «Работа с потреблением» — выгрузка потребителей по группам (Физлица, Юрлица, Потери) с суммами | меню «Утилиты» | 101 |
| Экспорт модели: **Файл → Экспорт** (или кнопка «Экспорт» подменю «Файл») → файл формата **\*.EPANET** | меню «Файл» | 19, 38 |
| Импорт модели: **Файл → Импорт** (\*.EPANET, SWMM) | меню «Файл» | 19, 37–38 |
| Файлы проекта: **\*.digwater** (открывается кликом); «Сохранить проект» / «Быстрое сохранение» | меню «Файл» | 18–19, 114 |
| Форма обратной связи вендору («О программе») — можно запросить доработку | главное меню → Программа | 109 |

**Честное замечание:** руководство **не описывает** сохранение отчётов в файл (Excel/Word/CSV).
Поэтому ниже — рабочий порядок действий и что просить у вендора.

### 3.2. Практический порядок (то, что работает уже сейчас)

1. Выполнить расчёт (кнопка «Расчет»), дождаться, проверить «Журнал расчета».
2. Поставить **регулятор времени** на нужный момент (например, 14:37, как на скриншотах).
3. Открыть нужный отчёт (меню «Отчёты»). Если таблица выделяется — попробовать
   `Ctrl+A` → `Ctrl+C` → вставить в Excel (часто работает в табличных вкладках).
4. Если не копируется — **сделать скриншот отчёта**: он в любом случае пригодится
   (для датасета это такой же полезный кадр «что здесь происходит», как карта).
5. Двигая регулятор времени и повторяя п. 3–4, можно собрать «покадровую» картину
   по времени для одного объекта (отчёт по объекту показывает значения именно на момент).

### 3.3. Что попросить у вендора (одно письмо, форма из п. 7.8.5, стр. 109)

> Для передачи результатов расчёта в систему обучения просим добавить/подсказать
> возможность выгрузки таблиц отчётов в Excel или CSV, а также выгрузки результатов
> расчёта по времени: по каждому участку/узлу — расход, скорость, напор/давление,
> статус, с шагом расчёта (CSV/XLSX или отчёт `.RPT`).

Если появится такая выгрузка — она закрывает «динамику» полностью: мы сможем сверять
числа в ответах (и в ответах нашей модели) не только по статике, но и по режиму во времени.

## 4. «Не понимаю, как достать `.inp` на момент съёмки»

Разберём по понятиям, потому что тут путаница естественная:

* **`.inp` — это модель (вход), а не результат.** Там параметры: узлы, трубы, диаметры,
  длины, шероховатость, насосы, правила, статусы задвижек. Расходов и давлений там нет —
  они появляются только после расчёта (см. §3).
* **Скриншот показывает и модель, и результаты** — карта с раскраской, свойства объекта.
* «Момент съёмки» для `.inp` важен только в одном случае: **если вы меняли модель** между
  кадрами (закрыли задвижку, поменяли режим насоса, правили параметры). Тогда просто
  делайте экспорт после каждого изменения.

**Порядок действий (максимум 20 секунд):** `Файл → Экспорт` → сохранить как
`Семей_ГГГГ-ММ-ДД_что-менял.inp`. Всё — это и есть «.inp на момент съёмки».

Если в тот же день не получилось — не страшно:
* для **статики** (диаметр, длина, шероховатость, отметки) подходит любой свежий экспорт
  того же проекта: эти поля между съёмками не меняются;
* для **динамики** нужна не `.inp`, а выгрузка результатов (см. §3.3);
* дополнительно можно хранить копии **проекта** (`*.digwater`, «Сохранить проект») по датам —
  из них `.inp` можно экспортировать когда угодно позже.

## 5. Отчёт ЕБРР: что уже вытащено и как его разметить

Из присланного отчёта (171 стр.) автоматически извлечено:

| Что | Сколько | Где в workspace |
|---|---|---|
| текст всех страниц | 170 740 знаков | `semey/report_text.json` |
| **таблицы** (числовые) | **29 таблиц, 3807 ячеек** | `semey/report_tables/*.csv` |
| картинки ≥300 px | 106 файлов (JPEG) | `semey/report/rep_*.jpg` |

Что с этим можно делать (по возрастанию трудозатрат):

1. **Сверка с моделью** — таблицы уже структурированы. Пример: «общая протяжённость
   940 355.41 м» и разбивка «Ø25 — 3400 шт, Ø50 — 3176 шт…» сходятся с `.inp`
   (там ровно 3400 труб Ø25 и 3176 Ø50). Такие сверки подтверждают, что документы и модель
   описывают один объект.
2. **Справочник терминологии** — из текста можно собрать «как правильно называть» (насосная
   станция, РЧВ, зона потребления, удельные потери) и добавить в инструкцию модели.
3. **Разметка картинок отчёта** (отдельный вспомогательный набор): разложить по типам
   (схема сети, график, карта, скриншот) и подписать 1–2 фразами — вручную или тем же Gemini.
   Получится мини-датасет «чтение отчётных схем». Важно: это **не** заменяет основной
   датасет (другой домен), поэтому хранить отдельной папкой и отдельной группой.

Коротко: отчёт — не «обучающие пары» для главной задачи, а **сырьё для знаний и сверок**.

## 6. Что можно вытащить из ответов Gemini (уже сделано)

Инструмент: `tools/extract_claims.py` — ищет в ответах проверяемые утверждения
(объект → параметр → значение) и сверяет с моделью.

```powershell
python tools\extract_claims.py --answers D:\Семей\датасет\export.jsonl `
       --inp "D:\Семей\модель для ИИ — копия.txt" --out D:\Семей\claims.csv
```

Результат на присланных 24 парах: **43 утверждения** — 24 «точно», 4 с уточнением единиц,
2 расхождения, 13 нечем проверить (в основном расходы — они требуют расчёта).

Примеры подтверждённых: «труба 3459843, Ø500, L=218.96» (совпало с моделью),
«скорость 0.12 м/с при Q=87.9» (пересчёт даёт 0.124 м/с — сходится с округлением),
«потери 0.11 м» — по модели это **удельные** потери 0.109 м/км (полные на участке 0.024 м).
Пример расхождения: Gemini пишет «удельные потери i 0.5 м/км» — по расчёту 0.109 м/км.

**Зачем это нужно:**
1. это готовый «проверяльщик выдуманных чисел» для будущей модели (тот же код пригодится в проде);
2. в датасет можно добавлять колонку «есть неподтверждённые числа» — и не учить модель на ошибках;
3. табличка `claims.csv` — отличный материал для быстрой ручной ревизии (см. §7).

## 7. Эталонов инженеров не будет — чем компенсировать

Это нормально, но зафиксируйте риски и компенсации (потом это попадёт в отчёт о приёмке):

1. **Автоматическая проверка чисел** по `.inp` — уже работает (см. §6). Ловит фактические
   ошибки Gemini (координаты, диаметры, единицы).
2. **Выборочная ревизия**: из ~300 кадров достаточно, чтобы кто-то из ваших инженеров
   пробежал `claims.csv` и пометил «ок / не ок» там, где числа не подтвердились (обычно
   это десятки строк, 20–30 минут). Это не «разметка системы», а разовая проверка.
3. **Приёмка по метрикам относительно Gemini** — мы измеряем «насколько модель отвечает
   как эталон», а не «истину». Это надо явно записать в критерии приёмки, чтобы потом
   не было спора.
4. **Честные отказы**: в датасете есть примеры, где непонятно — модель должна уметь
   говорить «на кадре недостаточно данных», это метрика `refusal_rate`.

Если появится возможность — самый ценный подарок от заказчика не «эталонные ответы на всё»,
а **замечания к 20–30 ответам**: где Gemini (и, значит, обученная модель) говорит чушь.

## 8. Обновлённый чек-лист запроса (под ваши возможности)

**Обязательно**
1. Скриншоты: цель 300–500+; разные окна (карта с темами, свойства объектов, отчёты,
   графики, журнал расчёта), разные проекты, разные моменты времени; PNG, полное окно.
2. Ответы Gemini на те же кадры, тем же вопросом, полным текстом.
3. Таблица пар (или папка + имена) — по §2.
4. `.inp` по каждому проекту — свежие экспорты (Файл → Экспорт), имя с датой.

**Желательно**
5. Результаты расчётов: пока — скриншоты отчётов и таблиц; в перспективе — запрос вендору
   на выгрузку (`Excel/CSV`/`.RPT`, см. §3.3).
6. Отчёты по проектам (PDF/DOCX) — текст, таблицы и картинки извлечём сами.
7. Письменное «ок» на использование материалов для обучения; и, по возможности, замечания
   инженеров к 20–30 кадрам (§7).

**Не нужно**
* пересланные через мессенджеры JPEG (мелкий текст нечитаем);
* инженерные эталоны «на всё» (без них работаем, см. §7);
* синтетические/демонстрационные данные в датасет (только в `tests/fixtures/`).
