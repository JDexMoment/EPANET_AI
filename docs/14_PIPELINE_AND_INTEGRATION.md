# 14. Как всё устроено: программа, датасет, обучение, интеграция

Этот документ отвечает на вопрос «что мы вообще строим, как это работает и как срастётся
с AquaBit». Читать после него — `docs/15_AQUABIT_DATA_HOWTO.md` (что конкретно делать руками).

---

## 1. Одна страница «на пальцах»

**Задача.** Есть ПО **AquaBit** (гидравлические расчёты сетей, форк EPANET). Инженер смотрит
на экран: карту, свойства объекта, отчёты, графики. Мы делаем **AI-помощника**, который
смотрит на тот же экран и по-русски объясняет, что там происходит: «это магистральный
водовод Ø500, расход упал с 87.9 до 65.4 м³/ч, скорость 0.09 м/с — застойная зона».

**Как это устроено.** Обучаем **небольшую локальную модель-зрение (VLM)** на парах
«скриншот AquaBit → текст-эталон». Эталон мы не пишем руками: заказчик уже прогнал
свои скриншоты через Gemini и получил разборы. Получается:

```
реальный экран AquaBit  →  [VLM-модель, живёт локально на ПК/сервере]  →  ответ на русском
                                   ↑
                    училась на 24+ парах «скриншот → ответ Gemini»
```

**Что уже есть у нас:** 24 такие пары (собранный датасет), конвейер их приёма и проверки,
план обучения, метрики, утилита работы с `.inp` AquaBit. **Что нужно от заказчика:**
ещё много скриншотов (иначе модель выучит один проект «Семей») и, по возможности,
выгрузки расчётов из AquaBit.

## 2. Пайплайн данных: из скриншотов — датасет обучения

```
 ① СБОР                       ② ПРОВЕРКА (QA)                ③ СБОРКА
┌───────────────────────┐    ┌────────────────────────┐    ┌──────────────────────┐
│ скриншоты AquaBit     │    │ дубликаты кадров (dHash)│    │ train / val / test    │
│      +                │ →  │ пустые/битые ответы     │ →  │ (по группам-сессиям,  │
│ ответы Gemini (.txt)  │    │ «выдуманные числа»      │    │  чтобы не было утечки)│
└───────────────────────┘    └────────────────────────┘    └──────────────────────┘
        │                             │                            │
        │  tools/prepare_pairs_worksheet.py                          │
        │  src.dataset.import_screenshots                            │
        │  src.dataset.check_screenshot_pairs                        │
        │                                        src.dataset.build_vl_dataset
        ▼
  data/screens/manifest.jsonl — единый список: картинка, вопрос, ответ, группа, отпечатки

  ФАКУЛЬТАТИВНО (но очень полезно):
  «модель .inp» + tools/extract_claims.py → проверка чисел в ответах Gemini по модели
                                            (см. §4 и docs/15, раздел 6)

  ДЛЯ ПРИЛОЖЕНИЯ (вариант A):
  src/model_io (чтение .inp/.NET/.epanet) + tools/assistant_prototype.py (карточка,
  расчёт, график) + VLM → docs/16_ASSISTANT_APP.md
```

Правила проекта: **в обучении только реальные данные** (скриншоты заказчика + его ответы),
синтетика — только в `tests/fixtures/` для автотестов. Проверка — `tools/check_data_purity.py`.

## 3. Пайплайн модели: из датасета — работающий помощник

```
 ④ ОБУЧЕНИЕ (GPU, аренда)              ⑤ СБОРКА (можно на CPU)         ⑥ РАБОТА (ПК клиента)
┌───────────────────────────┐        ┌──────────────────────────┐   ┌─────────────────────┐
│ Qwen3-VL-4B-Instruct      │        │ LoRA-веса + база → merge │   │ llama-server.exe    │
│ + LoRA в языковой части   │   →    │ → convert_hf_to_gguf     │ → │ модель GGUF (Q4)    │
│ (зрение заморожено)       │        │ → llama-quantize Q4_K_M  │   │ + mmproj (зрение)   │
│ src/train/vl_lora.py      │        │ ≈2.5 ГБ + mmproj 0.8 ГБ  │   │ офлайн, без сети    │
└───────────────────────────┘        └──────────────────────────┘   └─────────────────────┘
                                                                              │
 ⑦ ПРИЁМКА: src/eval/metrics_vl.py — сравнение ответов с эталоном по метрикам:
    numbers_f1 (числа), ids_f1 (ID объектов), meaning_f1 (смысл), grounding (нет ли
    выдуманных чисел), hallucinated_n, refusal_rate (честные отказы), length_ok_rate.
```

Требования: обучение — арендованная GPU (4B-модель с LoRA ≈ 8 ГБ, QLoRA ≈ 4.4 ГБ);
работа у клиента — обычный ПК: 4-битное квантование укладывается в несколько ГБ ОЗУ,
GPU не обязательна. Всё локально, интернет не нужен.

## 4. Роль `.inp` и отчётов: три разные задачи

Частое смешение: думают, что `.inp` — «тоже данные для обучения». Нет. У него три других роли:

| Роль | Когда работает | Что даёт |
|---|---|---|
| **1. Проверка эталона** | при сборке датасета | сверяем числа из ответов Gemini с моделью (`tools/extract_claims.py`): на 24 парах нашлось 43 утверждения, 28 подтвердились, 2 расхождения, 13 нечем проверить |
| **2. Проверяльщик готовой модели** | при работе помощника | если модель назвала расход/скорость/диаметр, которые противоречат `.inp` — ответ отправляется на доработку или помечается предупреждением |
| **3. Подсказка модели (grounding)** | при работе помощника, продвинутый вариант | вычислить по `.inp` нужные значения (скорость, удельные потери) и положить их в контекст — модель реже ошибается в числах |

Отчёты (например, отчёт ЕБРР по Семею) — это **база знаний и справочник терминологии**:
из них извлечены текст (170 740 знаков), 29 таблиц и 106 картинок; их используют для
единообразия языка ответов, как источник нормативных значений и как отдельный материал
для разметки (см. `docs/15`, раздел 5).

## 5. Варианты интеграции с AquaBit

По убыванию трудозатрат заказчика:

### Вариант A — «Помощник рядом» (рекомендуемый старт)
Отдельная программа на том же ПК: инженер делает скриншот (Print Screen или кнопка)
→ перетаскивает в окно помощника **вместе с файлом модели** (`.inp`, `.NET`, `.epanet`)
→ получает разбор, точные данные из модели, расчёты, графики и отчёты. Ничего в AquaBit
менять не нужно, производитель ПО не при делах.
**План и архитектура приложения — `docs/16_ASSISTANT_APP.md`; рабочий прототип карточки —
`tools/assistant_prototype.py`.**

```
[AquaBit на экране] --PrintScreen--> [файл .png] --перетащил--> [Помощник: VLM локально] --> ответ
```

**Что нужно:** обученная модель (этапы ④-⑥), простейшее окно/скрипт. Это то, что
покрывает текущая работа.

### Вариант B — «Кнопка в AquaBit» (позже, если вендор согласится)
Вендор добавляет кнопку/пункт меню «Спросить AI», который сам делает снимок текущего
окна и отдаёт его локальной модели. Никакой пересылки данных наружу.

**Что нужно:** согласие и работа вендора («ЭкоИнфраИнжиниринг», форма обратной связи —
руководство AquaBit, стр. 109), интерфейсный контракт (какие данные окна передавать).

### Вариант C — «Сервер на несколько инженеров»
Помощник живёт на сервере предприятия; инженеры работают через веб-страницу. Полезно,
если ПК слабые и моделей несколько (модель «понимает» разные проекты).

**Что нужно:** сервер с GPU (или сильный CPU), корпоративная сеть, политика доступа.

### Где здесь `.inp`
Автоматическая связка «скриншот ↔ модель сети»: если помощник знает, какой проект открыт и
где лежит его `.inp`, он может сам подтянуть параметры. Это план на этап после приёмки —
сначала помощник должен уверенно отвечать «по глазам».

## 6. Что уже готово и что дальше

**Готово:** приём и проверка датасета (24 пары, все чистые), сборка сплитов, план обучения
и скрипты под ms-swift/TRL, метрики с порогами, утилита `.inp` (сводка/поиск/проверка
чисел/конвертация), извлечение утверждений из ответов, автотесты (`bash tools/smoke_test.sh`).

**Дальше по шагам:**
1. заказчик присылает **ещё скриншоты + ответы Gemini** (цель 300–500+, разные окна/проекты);
2. прогон через конвейер (одна команда), QA, сплиты;
3. аренда GPU → обучение LoRA → приёмка по метрикам;
4. сборка GGUF под клиента, проверка на их ПК;
5. пилот: инженеры работают месяц, присылают замечания; добор данных → вторая итерация.

## 7. Словарь (чтобы не путаться)

| Термин | Что значит |
|---|---|
| **VLM** | модель, которая «видит» картинки и пишет текст (у нас — Qwen3-VL) |
| **Пара** | скриншот + ответ-эталон на него. Датасет — набор пар |
| **Манифест** | служебный список пар (пути, метаданные, отпечатки) — `manifest.jsonl` |
| **Сплит** | деление датасета на train / val / test, чтобы честно измерять качество |
| **LoRA** | «насадка» на большую модель: учим 1–3% весов, быстро и без огромных GPU |
| **GGUF / Q4_K_M** | формат и 4-битное сжатие модели для запуска на обычном ПК |
| **mmproj** | отдельный файл «зрения» для VLM при запуске в llama.cpp |
| **dHash** | отпечаток картинки; им ловим дубликаты кадров и утечки между train/test |
| **Grounding** | доля чисел ответа, подтверждаемых данными (`.inp`, текст экрана) |
| **`.inp`** | текстовый экспорт модели сети из AquaBit (совместим с EPANET) |
| **Отчёт (в AquaBit)** | вкладки с таблицами/графиками после расчёта (меню «Отчёты») |
