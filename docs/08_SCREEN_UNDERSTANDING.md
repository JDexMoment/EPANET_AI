# Понимание экрана (screen understanding)

## 1. Решение

От CV/VLM-модели отказались сознательно. Вместо «модель смотрит на картинку» делаем
**детерминированное определение содержимого экрана**:

```
скриншот → OCR + геометрия блоков + словари (configs/ui.yaml)
         → JSON «что на экране» (schemas/screen.schema.json)
         → блок ui внутри llm_context  →  ОБЫЧНАЯ текстовая LLM
```

Пиксели в LLM не уходят никогда. Уходят только факты: тип экрана, выбранный объект,
шаг времени, видимые значения и действия — всё с явной уверенностью.

## 2. Почему без CV-модели

| Причина | Что это даёт |
|---|---|
| Приватность и «клиентский ПК» | 0 ГБ VRAM на зрение, работает на CPU без GPU |
| Объяснимость | каждый вывод можно проверить: вот OCR-блок, вот правило — видно, почему выбран J-105 |
| Стоимость поддержки | нет второй нейросети, которую надо обучать, версионировать и обновлять |
| Доверие к числам | значения берутся из OCR-текста интерфейса, а не «угадываются» по картинке |
| Надёжность | ошибки зрения локализованы и измеримы (см. метрики ниже), а не «иногда VLM галлюцинирует» |

Дополнительный аргумент: если CV/VLM-модель «смотрит» на картинку и сама называет числа,
мы теряем главный контроль качества проекта — правило «каждое число подтверждено фактом E-xxx».

## 3. Что именно определяется

| Поле | Пример | Как используется |
|---|---|---|
| `screen_type` | `map`, `results_table`, `object_editor`, `time_series`, `report`, `form`, `dialog` | выбор режима ответа и подсказки пользователю |
| `selected_object` | `J-105` (из подписи, поля панели или легенды графика) | подстановка в `selection` → focus-контекст по этому объекту |
| `timestep` | 8.0 ч | «на шаге 8 ч давление…»; иначе ассистент отвечает по суткам |
| `visible_objects[]` | `J-105 = 9.96 м вод.ст.` | проверка: числа, которые видит инженер, совпадают с расчётом |
| `panels[]` | `[map, results_table]` | понимание компоновки экрана |
| `actions[]` | `focus_entity(J-105)`, `set_timestep(8)` | ассистент может предложить готовое действие в интерфейсе |
| `ambiguity` | `{level: high, notes: [...], candidates: [...]}` | политика «не угадывать»: сначала уточняющий вопрос |

Всё это оказывается в `llm_context.request.ui`:

```json
{
  "screen_type": "map", "selected_object": "J-105", "object_type": "junction",
  "timestep_h": 8.0, "confidence": 0.98,
  "description_ru": "Пользователь смотрит на карту сети. Выбран объект J-105. Расчётное время — 8 ч. На экране видны значения: J-105 — 9.96 м вод.ст..",
  "source": "screen_understanding", "actions": ["select_object", "focus_entity"],
  "ambiguity": "low", "mode_auto": "why_happened"
}
```

Режим ответа выбирается автоматически (`mode_for`): экран + вопрос → `why_happened`,
`explain_object`, `whats_happening`, `make_report`.

## 4. Как это устроено (три уровня)

| Уровень | Что делает | Стек | Когда включать |
|---|---|---|---|
| **1. Базовый (уже работает)** | OCR + геометрия + словари: тип экрана, объекты, значения, шаг времени | `src/vision/detect_screen.py` + `configs/ui.yaml`; RapidOCR / PaddleOCR / Tesseract | сейчас, даёт MVP |
| **2. Классификатор типа экрана** | маленькая CNN/ONNX-модель (MobileNet/EfficientNet-B0, 5–15 МБ, CPU < 100 мс) вместо эвристик для `screen_type`/`panels` | обучение на 300–1000 размеченных скриншотах (разметчик: `tools/label_screen.html`) | если точность типа экрана < 0.95 или интерфейс сильно меняется |
| **3. Мини-VLM (опция)** | Qwen3-VL 2B/4B (>2–3 ГБ) — читает сложные графики и тултипы | локально, CPU/GPU | только если OCR структурно не справляется; решение — по цифрам бенчмарка |

Уровень 2 не требует GPU: это обучение на несколько часов и инференс 5–15 МБ на CPU —
на порядки дешевле, чем «прикрутить 80B-VLM только для зрения».

## 5. Данные и разметка экранов

1. Скриншоты кладите в `data/screen_labels/screenshots/` (реальные экраны приложения,
   разные: карта, таблица, панель свойств, график, отчёт; светлая/тёмная тема; 100 %/150 % DPI).
2. Откройте `tools/label_screen.html`, перетащите скриншот, заполните поля и нажмите «Экспорт JSON».
3. Файл сохраняется как `data/screen_labels/screen_<id>.json` в формате
   `{screen_id, file, labeler, golden: {...}}`.
4. Прогон и оценка:
   ```bash
   python -m src.vision.detect_screen --image data/screen_labels/screenshots/map_01.png \
       --inp data/raw/<ваша_сеть>.inp --out data/screen_labels/screen_map_01.json
   python -m src.eval.metrics_screen --labels data/screen_labels --pred data/screen_labels/predictions.jsonl
   ```
5. Сколько нужно: 60–100 экранов — рабочая проверка; 300–1000 — для обучения уровня 2.
   Тяжёлые случаи обязательны: два объекта рядом, мелкий шрифт, тултип поверх подписи,
   свёрнутые панели, вкладки.

## 6. Метрики и пороги (`configs/ui.yaml → acceptance`)

| Метрика | Порог | Почему именно так |
|---|---|---|
| `screen_type_accuracy` | ≥ 0.95 | тип экрана задаёт режим ответа |
| `selected_object_accuracy` | ≥ 0.95 | разбор «не того узла» хуже отсутствия ответа |
| `wrong_object_rate` | ≤ 0.01 | **главная метрика риска**: молчаливая ошибка выбора объекта |
| `value_binding_accuracy` | ≥ 0.90 | числа на экране должны совпадать с расчётом |
| `timestep_accuracy` | ≥ 0.95 | допуск ±1 ч |
| `action_f1` | ≥ 0.80 | предложенные действия не должны раздражать пользователя |
| `abstention_rate_on_ambiguous` | ≥ 0.90 | на неоднозначном экране ассистент ОБЯЗАН спросить |

Демо-прогон на 6 синтетических экранах (проверка инструмента, не бенчмарк):

```bash
python -m src.eval.metrics_screen --labels tests/fixtures/screen_demo   # демо-проверка инструмента
→ screen_type 1.00 · selected_object 1.00 · wrong_object 0.00 · values 1.00 · timestep 1.00 · actions F1 1.00 · abstention 1.00
```

Результаты: `data/eval/screen_scores.demo.json`. Реальный бенчмарк появится после разметки
настоящих скриншотов (папка `data/screen_labels/`).

## 7. Политика «не угадывать»

`src/vision/screen_to_context.py` перед ответом проверяет:

1. **уверенность < 0.60** или **ambiguity = high** → `{action: ask_user, candidates: [...]}`;
2. объект есть, но **не найден в сети расчёта** → уточняющий вопрос + список объектов сети;
3. два объекта с близкими оценками и вопрос со словами «этот/здесь/выбранный» → уточняющий вопрос;
4. иначе — обычный ответ с пометкой об неоднозначности в `ui.ambiguity`.

Такой отказ — не сбой, а требование: лучше спросить, чем выдать корректный разбор не того узла.

## 8. Ограничения и как их обойти

| Ситуация | Что происходит | Решение |
|---|---|---|
| Скалирование 150–200 % | OCR мельче, блоки дробятся | инструктировать DPI; подавать реальный скриншот, не масштабированный |
| Захват «под курсором» | подпись перекрыта тултипом | сделать 2 кадра (до/после наведения) или захват только активного окна |
| Два монитора | координаты склеиваются | захватывать окно приложения (PrintWindow/BitBlt), а не рабочий стол |
| График без подписей | объект не определяется | брать объект из заголовка панели/легенды; иначе — уточняющий вопрос |
| Анимация (мигание выбранного) | ложные срабатывания | усреднять 2–3 кадра по времени |

## 9. Что нужно от продукта

* Захват скриншота активного окна по кнопке (или по «горячей клавише») — Windows: `PrintWindow`;
  веб-версия: `canvas` панели. Скриншот не покидает машину.
* Разрешение: обычно достаточно `screen_type` + `selected_object` + `timestep`;
  полный `ui_context` — когда пользователь задал вопрос.
* Никаких сетевых вызовов: OCR локальный.

## 10. Место в дорожной карте

* Этап 2 (ассистент) — уровень 1 даёт работу «смотри, что у инженера на экране» без CV-модели;
* Этап 3 (интеграция) — `actions[]` позволяют ассистенту предлагать действия в UI;
* Этап 4 (fine-tune) — данные об экране идут в тот же SFT-набор: модель учится отвечать
  на «инженер смотрит на карту и выбрал J-105» ровно так, как отвечал эксперт.
