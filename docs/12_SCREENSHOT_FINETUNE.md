# Скриншоты → ответ: что меняется и как это делать

Новая вводная: заказчик присылает датасет — **скриншоты программы** и **«золотые» ответы Gemini**
на вопрос «что здесь происходит». Нужно локально воспроизвести такое же поведение: та же модель,
но у нас, без интернета и без облака.

---

## 1. Главный вопрос: возвращать ли CV-модель

**Коротко: отдельная CV-модель не нужна. Но «зрение» вернуть придётся — в виде одной модели.**

Что было раньше в проекте:

| Схема | Что это | Вердикт |
|---|---|---|
| **A. Отдельная CV + текстовая LLM** (то, что отклонили) | CV-модель детектит элементы → факты текстом → текстовая LLM отвечает | Не возвращаем: два контура обучения, ошибки детекции необратимо теряются по дороге, «что происходит» по сетке/графику так не рассказать |
| **B. VLM: одна модель, картинка на входе** | vision-encoder + языковая часть в одном чекпойнте; учим LoRA на парах «скриншот → ответ» | **Рекомендуется.** Это ровно то, чем является Gemini: учим модель на его ответах, а не пересказываем их своими словами |
| **C. OCR + текстовая LLM** (без нейросетевого зрения) | OCR вытаскивает текст с экрана → наша текстовая модель отвечает по этому тексту | Не тянет «что происходит»: графики, профили, схемы сети, цвета, подсветка аварий — всё это не текст. Оставляем как **резерв для самых слабых ПК** и как **проверяльщика чисел** |

**Можно ли обойтись без зрения совсем?** Только если информацию с экрана можно восстановить из
чего-то ещё — например, у нас есть сам `.inp` и известен расчёт, а скриншот лишь иллюстрация.
Тогда да, хватило бы текстовой модели (наш прежний трек). Но в присланном датасете есть только
картинки: то, что нужно модели, существует **только в пикселях**. Значит зрение обязательно.

**Где старая работа не пропала:**
- `src/vision/detect_screen.py` (OCR + эвристики) остаётся — но не как «глаза» модели, а как
  **независимый проверяльщик**: если модель в ответе называет число, которого нет в OCR-тексте экрана,
  это сигнал выдумки (метрика `hallucinated_number_rate`);
- `src/vision/preprocess.py` — препроцессинг: привести к ~1M пикселей, вырезать и увеличить фрагмент
  с мелким текстом (таблица узлов читается заметно лучше);
- сервис сбора данных (перенесён в `archive/service/`) пригодится только если заказчик **вернёт** разметку инженеров: он может
  принимать не только модели, но и скриншоты с эталонными ответами.

## 2. Что за модель и на чём считать

Выбор (записан в `configs/vision.yaml`, решение по состоянию на 06.10.2026):

| Условие у клиента | Модель | Размер на диске | Скорость ответа |
|---|---|---|---|
| Нет GPU, 8-16 ГБ RAM (базовый случай) | **Qwen3-VL-4B-Instruct**, GGUF `Q4_K_M` | ≈ 2.5 ГБ + mmproj 0.8 ГБ | 20–60 с на CPU |
| Есть GPU 8-12 ГБ | **Qwen3-VL-8B-Instruct**, `Q6_K` | ≈ 3.7 ГБ + 0.8 ГБ | 2–5 с |
| Очень слабый ПК (4-8 ГБ RAM) | Qwen3-VL-2B-Instruct | ≈ 1.5 ГБ + 0.8 ГБ | 10–25 с на CPU |

Почему так:
- `llama.cpp` умеет Qwen3-VL с 30.10.2025 (компонент `mmproj` — «глаза» модели), то есть у клиента
  нужен только один бинарник, без Python, torch и интернета;
- **варианты «Thinking» не берём**: в 3-10 раз медленнее, а для «прочитать экран и рассказать»
  выигрыша нет;
- обучение идёт **LoRA в языковой части**, vision-энкодер замораживается (`freeze_vit`): так
  помещается в одну GPU и не разрушает способность видеть картинки.

Что нужно для обучения: **одна GPU на несколько часов** (можно арендовать). У клиента GPU не нужен.

## 3. Что делаем с присланным датасетом (пять шагов)

Код готов и проверен на демо-данных (`tests/fixtures/screens_pairs/`), команды — по порядку.

```bash
# 0. положить присланное в data/screens/raw/ (картинки + ответы в любой раскладке)

# 1. импорт: сшивает скриншоты с ответами, считает отпечатки
python -m src.dataset.import_screenshots --src data/screens/raw
#    понимает: выгрузку одним файлом (jsonl/json/csv), ответы отдельными файлами,
#    ответы рядом с картинками, отдельный текст экрана (OCR) — см. шапку модуля

# 2. контроль качества: дубли, отказы, обрывки, подозрительные числа
python -m src.dataset.check_screenshot_pairs --strict

# 3. сплиты train/val/test по группам + форматы тренеров
python -m src.dataset.build_vl_dataset --copy-images

# 4. обучение (на машине с GPU): план, затем сам запуск
python -m src.train.vl_lora --print-plan
python -m src.train.vl_lora --emit-script outputs/train_vl.sh      # ms-swift
python -m src.train.vl_lora --backend transformers --emit-script outputs/train_vl.py
#    затем на GPU-машине:  bash outputs/train_vl.sh   (или python outputs/train_vl.py --smoke)

# 5. оценка на отложенной выборке
python -m src.eval.metrics_vl --ref data/screens/eval_reference.jsonl \
    --pred base=outputs/base_pred.jsonl --pred ours=outputs/ours_pred.jsonl
```

Что получается в `data/screens/`: `manifest.jsonl` (все пары), `qa_report.json`,
`train/val/test.jsonl` (канонический вид), `swift_*.jsonl` и `sharegpt_*.jsonl` (готовые форматы),
`eval_reference.jsonl` (эталон для метрик), `images/` (рабочие копии картинок).

## 4. Три вещи, на которых такой датасет обычно ломается

**1. «Утечка» похожих кадров.** Скриншоты одной сессии почти одинаковы: тот же экран, другие цифры.
Если делить случайно, одна и та же картинка окажется и в train, и в test — метрики будут красивыми
и бесполезными. Решение в коде: dHash-отпечаток + расстояние Хэмминга ≤ 8 → один кластер;
сплиты делятся **по группам** (сессия/кластер), и группа никогда не рвётся между выборками.
Проверено: 20 сессий по 3 кадра → 48/6/6, ни одна сессия не попала в две выборки.

**2. Ошибки самого Gemini в «золотых» ответах.** Gemini тоже не всегда верно читает мелкий текст:
может назвать число, которого на экране нет. Слепо учить на этом — тиражировать ошибку. Решение:
- `check_screenshot_pairs` сверяет **точные числа** (с дробной частью) ответа с OCR-текстом экрана и
  выносит их отдельным списком: `числа с дробной частью, которых не видно на экране`;
- круглые числа (25, 46) — это обычно нормативы и округления, они в список «выдумок» не попадают;
- метрика `hallucinated_number_rate` считает то же самое уже у нашей модели;
- на реальном датасете стоит просмотреть глазами 30-50 отмеченных пар — это первое, что я сделаю,
  когда данные будут на руках.

**3. Перекос и объём.** Если 90 % скриншотов — один экран с разными числами, модель выучит этот
экран и не научится остальным. В отчёте видно распределение по группам и размерам; если перекос
сильный — либо добираем редкие типы, либо (позже, осознанно) аугментируем.

## 5. Метрики: как понять, что «стало как у Gemini»

Меряем не «красиво ли написано», а проверяемые вещи (пороги — в `configs/vision.yaml`):

| Метрика | Что значит | Порог |
|---|---|---|
| `numbers_f1` | совпадение чисел с эталоном (допуск 2 %: 22.09 ≈ 22.1) | ≥ 0.75 |
| `ids_f1` | совпадение ID объектов (J105, P-106, R-1) | ≥ 0.80 |
| `meaning_f1` | о том ли вообще ответ (пересечение значимых слов) | ≥ 0.55 |
| `grounding_rate` | доля чисел ответа, подтверждённых текстом экрана | ≥ 0.95 |
| `hallucinated_number_rate` | выдуманные числа | ≤ 0.05 |
| `refusal_rate` | «не могу определить» там, где ответ был известен | ≤ 0.05 |

Проверка самих метрик (демо-датасет): ответ, равный эталону, даёт 1.0 по всем пунктам;
«испорченный» ответ (стерты числа, добавлено 99.99, часть — отказы) — `numbers_f1` 0.50,
`hallucinated_number_rate` 0.50, `refusal_rate` 0.33. Метрики различают качество, а не просто
печатают числа.

Отдельно смотрите список худших примеров в конце отчёта: 5-10 картинок с наименьшим `numbers_f1`
почти всегда объясняют, чего модели не хватает.

## 6. Чего стоит попросить у заказчика (это сильно упростит работу)

Датасет самодостаточен, но если получится добрать метаданные — качество вырастет:

1. **Формулировку вопроса** в том виде, в каком её задавали Gemini (и различалась ли она).
2. **К какой модели/сети** относится скриншот (имена файлов) — чтобы группировать сессии.
3. **Какое окно** на скриншоте (таблица узлов, профиль, схема, отчёт) и какое **время расчёта**.
4. **Если сохранились `.inp`** — это позволит потом проверять ответы по расчёту, а не только по OCR.
5. **Скриншоты без пережатия** (PNG, не мессенджерский JPEG): на мелком тексте разница решающая.
6. Понимание, **где ответы Gemini заведомо слабые** (сам заказчик обычно это знает).

Всё это — не блокеры: пайплайн стартует на том, что пришлют.

## 7. Приватность и автономность

Данные заказчика (скриншоты производственных сетей) — чувствительные:
- импорт, контроль качества, обучение и оценка выполняются **локально**, ничего не уходит в сеть;
- у клиента модель работает через `llama-server` на `127.0.0.1` — без интернета;
- в репозиторий не попадают ни картинки, ни ответы: `data/screens/raw/`, `images/` и `*.jsonl`
  перечислены в `.gitignore`;
- синтетические фикстуры (`tests/fixtures/screens_pairs/`) — только для проверки кода.

## 8. План работ

| Этап | Что делаем | Оценка |
|---|---|---|
| 1 | Импорт присланного, отчёт контроля качества, разбор спорных пар глазами | 0.5–1 день |
| 2 | Сборка сплитов, базовая оценка **нетронутой** модели (baseline) на отложенной части | 1 день (нужна GPU для прогона предсказаний) |
| 3 | Обучение LoRA (первая итерация), оценка, разбор худших примеров | 1–2 дня |
| 4 | Повтор обучения с добавлением проблемных типов, подбор размера картинок и кропов | 1–2 дня |
| 5 | Квантизация в GGUF + mmproj, локальный запуск у клиента, замер скорости на его ПК | 1 день |
| 6 | Инструкция «как пользоваться» + приёмка по метрикам | 0.5 дня |

Что нужно от вас: GPU-машина на этапы 2-4 (аренда на несколько часов) и решение по модели
(4B по умолчанию; 8B — если у клиента есть GPU).

## 9. Честные оговорки

- Обучение в этой среде не запускалось: здесь нет GPU и torch. Проверено всё, что можно проверить
  без модели — импорт, контроль качества, деление по группам, сборка форматов, план обучения,
  метрики (на демо-данных). Скрипты обучения генерируются готовыми к запуску и проверены на синтаксис.
- Метрики `numbers_f1`/`ids_f1` сравнивают с ответами Gemini, а не с «истиной». Если Gemini ошибся в
  датасете, идеальная модель получит заниженную оценку. Поэтому и существует сверка с OCR-текстом
  экрана — она не зависит от Gemini.
- VLM на CPU отвечает десятками секунд. Если клиенту нужна «мгновенность» — либо GPU, либо
  резервный путь C (OCR + текстовая модель) для простых экранов.
