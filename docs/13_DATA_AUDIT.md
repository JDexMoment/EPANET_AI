## 3. Проверка чисел Gemini по модели: сходится (выборка из 3 участков)

Модель на скриншотах и присланный `.inp` — **один и тот же проект**. Проверено по трём
участкам, которые Gemini назвал по ID: сверили параметры из `.inp` и пересчитали
скорость `V = Q / A` и удельные потери `i` по Хазену–Вильямсу (`10.67·L·Q^1.852/(C^1.852·D^4.87)`).

| Труба (ID) | Gemini | В `.inp` | Пересчёт | Итог |
|---|---|---|---|---|
| 3459843 | Ø500 мм, L = 218.96 м, V = 0.12 м/с, потери 0.11 | Ø500, L = 218.96, C = 75 | при Q=87.9: V = **0.124**, i = **0.109 м/км** | ✅ |
| 3459843 (день) | V = 0.09, потери 0.06 при Q = 65.4 | — | V = **0.093**, i = **0.063 м/км** | ✅ |
| 3427706 | Ø400 мм, V = 1.68 при Q = 759.6 | Ø400, C = 75 | V = **1.679** | ✅ |
| 3459874 | Ø200 мм, V = 0.00 при Q = 0.3 | Ø200, C = 75 | V = **0.003** | ✅ |

Выводы:

1. Ответы Gemini **арифметически корректны и привязаны именно к этой модели** — их можно
   использовать как золото, но проверять, а не доверять слепо.
2. «Потери» в ответе — **удельные (м/км)**, а не полные метры на участке: 0.0238 м полных
   против 0.109 м/км. Модель легко перепутает эти величины — в промпте нужно явно требовать единицы.

Инструмент для таких проверок: `tools/aquabit_inp.py`


## 4. Границы применения `.inp`: статику — можно, динамику — только через AquaBit

### 4.1. Особенности формата AquaBit (всё уже обрабатывается)

| Особенность | Что именно | Чем лечится |
|---|---|---|
| Кодировка cp1251 | комментарии вида «;НС», «;разрешения» | авто-декодер в `tools/aquabit_inp.py` |
| Статус трубы на месте minor loss | 117 строк: `Closed` — 96, `Open` — 18, `CV` — 3 | `convert`: вставляет `0` в 7-е поле, статус остаётся 8-м |
| Комментарии в конце строк данных | `Closed;Недействующая`, `;Джесовский водовод` | обрезка по `;` при разборе |
| Кастомная секция `[PRESS]` | 66 строк вида `3381717 3381895 0 P3381920` | `convert` вырезает (семантику нужно уточнить у заказчика) |
| Кастомные опции | `SmoothPattern No`, `Overdemand`, `MinStepFreq 0.001`, `PrecPress 0.1`, `ALLOWPUMPREV No`, `PumpMinInp -10` | `convert` удаляет |
| Одноточечные кривые насосов | напр. `(0.347, 60 м)` — одна точка | в ванильном EPANET ведёт себя иначе |

Команда: `python tools/aquabit_inp.py convert --inp <файл> --out <файл_epanet.inp>`
→ WNTR после конвертации читает модель целиком (**21 069 узлов, 21 488 участков**).

### 4.2. Почему полный расчёт в ванильном EPANET не повторяет AquaBit

Проверено на реальной модели:

- расчёт идёт: сутки с шагом 15 мин — **505 с**, 97 срезов;
- но результат **нефизичен**: медиана давления 1,5 м, отрицательное давление у 9 852 узлов
  из 21 069, расходы по участкам ~0;
- причина: режим работы задаётся кастомной логикой Engine64 — насосы в `[STATUS]` закрыты и
  включаются 216 строками `[RULES]` по уровням 4 баков, а кастомные опции (`Overdemand`,
  `PumpMinInp`, `ALLOWPUMPREV`, `MinStepFreq`, `PrecPress`) и секция `[PRESS]` в ванильном
  EPANET отсутствуют; к тому же в `.inp` статусы насосов зафиксированы «Closed» (экспорт сделан,
  похоже, без выполненного расчёта).

**Практическое правило:**

* статика (D, L, C, отметки, спросы, паттерны, правила) → берём из `.inp`;
* кинематика от известного Q (V, i, h) → считаем формулами, сходится с Gemini;
* **динамика (Q, P, H во времени, статусы) → считать в AquaBit** и забирать из него таблицы
  результатов (см. §5, п. 4).

## 5. Что запросить у заказчика (чек-лист, по приоритету)

### Критично для обучения

1. **Ещё скриншоты** — 24 пары это затравка. Минимум 300–500 пар «скриншот + текстовый ответ»,
   цель 1000+; чем разнообразнее, тем лучше:
   * разные **типы окон**: карта с раскраской (диаметр/высота/скорость/давление), редактор
     свойств объекта, таблицы результатов, профиль, отчёты/ошибки расчёта, панель правил,
     зонирование, насосные станции;
   * **разные проекты** (не только Семей), режимы (0:00 / 14:37 / пик), версии модели;
   * разные масштабы (весь город / микрорайон / один узел).
2. **Формат скриншотов:** PNG **без пережатия**, полное окно программы, ширина ≥ 1600 px,
   без обрезки панелей и без перекрытия тултипами.
3. **Таблица пар** (CSV/XLSX/JSONL — любое), обязательные поля:
   `image`, `question`, `answer`;
   желательные: `session`/`project`, `network_file`, `timestamp`, `window_type`,
   `result_timestamp` (время расчёта, если видно на экране), `screen_text` (выгрузка OCR или
   текст, видимый на экране) — он нужен детектору выдуманных чисел.
4. **Экспорт результатов расчёта из AquaBit** — это закрывает динамику:
   * таблицы «ID × время»: расход Q, скорость V, напор/давление, статус, для тех же срезов,
     что на скриншотах (CSV/XLSX);
   * отчёт `.RPT` тех же расчётов;
   * если AquaBit умеет — выгрузка во время съёмки каждого скриншота.

### Желательно

5. `.inp` **в редакции на момент съёмки** (дата экспорта) — привязка «скриншот ↔ состояние модели»;
   в идеале — с выполненным расчётом (чтобы `[STATUS]` насосов отражал реальный режим).
6. **Документация кастома AquaBit** (от разработчиков): семантика `[PRESS]`, `Overdemand`,
   `PumpMinInp`, `ALLOWPUMPREV`, `MinStepFreq`, `PrecPress`, `SmoothPattern`; формулы движка;
   чему равна шероховатость 75 при H-W (С = 75?).
7. **Типовые вопросы инженеров** (5–20 формулировок), на которые должен отвечать модуль;
   и **эталонные ответы инженера** хотя бы на 30–50 кадрах — чтобы откалибровать «золото» Gemini
   и найти, где он ошибается (важно: ответы Gemini — не истина в последней инстанции).
8. **Грубая разметка «что на экране»** (тип окна, тема раскраски, время среза) — можно в той же таблице.
9. **Письменное разрешение** на использование скриншотов/модели в обучении и внутренних
   экспериментах (данные городской инфраструктуры).

### Чего не нужно

* пересланные картинки мессенджеров, повторно сжатые PNG/JPEG — теряется мелкий текст;
* скриншоты без ответа как «мусор для предобучения» — только с ответом или с пометкой «без ответа»;
* картинки отчёта (схемы, графики) вперемешку со скриншотами интерфейса без признака типа —
  домен другой, лучше отдельной папкой (у нас уже так: `semey/report/`).

## 7. Оговорки

* Выборка проверки чисел — 3 участка из ~14 ответов с ID. Хорошая новость: все сошлись; плохая —
  систематические ошибки Gemini так не поймать, нужна разметка инженера (§5, п. 7).
* Одна презентация = один проект = один стиль кадров. Модель, обученная на 24 таких парах,
  «выучит Семей», а не «поймёт экран» — поэтому п. 1–2 чек-листа критичны.
* Ответы Gemini содержат markdown/LaTeX (`$50 - 100\text{ мм}$`) — перед обучением нужна нормализация
  (уже отмечает QA как «замечание»).
* Расчёт в ванильном EPANET нефизичен из-за кастома — **не** строить на нём выводы о сети;
  для валидации динамики использовать экспорт AquaBit.
* Полный суточный расчёт в ванильном EPANET создаёт ~1 ГБ временных файлов — запускать только
  с ограничением шага/периода и с рабочим каталогом вне репозитория.
