# Выбор модели и развёртывание у клиента

Этот файл отвечает на два вопроса: **какая LLM подходит проекту** и **где она может работать**,
с учётом жёсткого требования: ассистент должен запускаться **у клиента** на «не самых мощных»
компьютерах (офисные ПК инженеров), без отправки данных наружу.

## 0. Решение (зафиксировано 05.10.2026)

| | |
|---|---|
| **Основная модель** | **`Qwen/Qwen3.5-9B`** — Apache 2.0, 9B, контекст 262К, ~5–6 ГБ в Q4 |
| Запасные | `Qwen3.5-4B` (8 ГБ RAM), `Qwen3.5-35B-A3B` (~18–20 ГБ, мощные машины) |
| Отклонено | `AliceAI-Foundation-80B-A3B-Base` — не запускается на клиентском ПК (разбор ниже) |
| Где зафиксировано | `configs/model.yaml` (читается `src/train/qlora_sft.py`), `docs/04_TRAINING.md` |

Почему Qwen3.5-9B: та же весовая категория, что Qwen3-8B (работает на 16 ГБ RAM без GPU),
но новее по качеству, длинный контекст и гибридное внимание Gated DeltaNet (24 из 32 слоёв —
линейное), поэтому KV-кэш не растёт квадратично с контекстом. Ниже — разбор отклонённого
варианта оставлен как обоснование решения.

## 1. Alice AI Foundation 80B-A3B: что это и почему не на клиентский ПК

Факты по релизу (сентябрь 2026):

| Параметр | Значение |
|---|---|
| Всего / активных параметров | 80 млрд / ~3 млрд на токен (MoE, 512 экспертов, top-10 + shared) |
| Архитектура | 48 слоёв, hidden 2048, гибридное внимание KDA + gated attention (3:1) |
| Контекст | 262 144 токена |
| Обучение | с нуля, ~18 трлн токенов, русский + английский |
| Лицензия | Apache 2.0, без гейта — коммерческое использование разрешено |
| Тип | **Base** (претрейн, без инструкционного тюнинга — chat-сборки нет) |
| Размер весов | **≈163 ГБ в BF16** (49 safetensors), ~45–48 ГБ в Q4 |

### Ключевое недоразумение

«Активных 3 млрд» — это про **вычисления на токен**, а не про память. Память определяется
общим числом параметров: 80 млрд × 2 байта = 163 ГБ, и даже 4-битная квантизация даёт
**≈45 ГБ только на веса**, плюс KV-кэш и буферы. То есть на «не самой мощной машине»
модель не запускается ни в каком виде: для Q4 нужно ~48 GB RAM/VRAM и больше,
для BF16 — 2-3 серверные карты класса 80 ГБ.

Дополнительные практические сложности:

* архитектура новая (`alice_ai`, KDA-внимание, `trust_remote_code`), официального GGUF нет;
  работающие квантизации — экспериментальные, от сообщества;
* для llama.cpp есть **кастомный патч** (стоковые llama.cpp / Ollama / LM Studio
  с этой архитектурой не проверялись) — то есть «поставим Ollama на ноутбуке и запустим»
  не работает; в публичном отчёте о запуске Q4 на машине с 128 ГБ памяти модель
  **не помещалась без swap**;
* это **базовая** модель: чтобы она вела себя как инженерный ассистент, её всё равно
  нужно инструктировать дообучать (LoRA) на нашем датасете — то есть +80 ГБ весов в цепочке
  «скачал → сконвертировал → обучил → запустил».

### Итог по AliceAI

Решение от 05.10.2026: **отклонён** для целей проекта. 80B весов не компенсируются 3B активных:
~45–48 ГБ только на веса плюс экспериментальный рантайм — это не клиентский ПК, а серверный
сценарий, который нам не нужен. Разбор сохранён здесь как запись о принятом решении.

## 2. Что реально влезает в клиентский ПК

| Вариант | Веса Q4 (без overhead) | Где работает | Комментарий |
|---|---|---|---|
| **Qwen3.5-9B — основной выбор** | ~5–6 ГБ | 16 ГБ RAM, CPU-only; или GPU 8 ГБ | Apache 2.0, 262К контекста, 24/32 слоя DeltaNet → KV-кэш почти не растёт; есть GGUF-сборки (unsloth) и MTP для спекулятивного декодирования |
| Qwen3.5-4B | ~3 ГБ | 8 ГБ RAM | для машин, где 9B не тянет; качество ниже на «почему» и отчётах |
| Qwen3.5-35B-A3B | ~18–20 ГБ | 32 ГБ RAM / 12–16 ГБ VRAM (+RAM-offload) | максимум качества для клиентов с нормальной машиной |
| AliceAI-80B-A3B | ~45–48 ГБ + патченный runtime | только сервер | не для клиента |

Ориентир по памяти: `RAM ≈ (параметры × бит / 8) × 1.2` (коэффициент — KV-кэш, буферы, роутинг).
Для нашего контекста (≤ 12 000 символов ≈ 4-6 тыс. токенов) KV-кэш у 8B измеряется сотнями МБ —
это не проблема. У MoE-моделей KV-кэш и активации больше: 35B-A3B требует ~20 ГБ и GPU/offload.

## 3. Про «русский язык»

AliceAI действительно сильнее на русских фактах (WikiWebFacts 86.5 против 62.4 у Qwen3.5-35B-A3B,
EduBench Russian 74.2 против 42.9). Но в нашей задаче проверяется **не знание мира**, а умение
объяснять гидравлику по числовым данным и не выдумывать значения:

* качество даёт не «русскость» весов, а дообучение на 200–500+ кейсах инженеров + жёсткий
  контекст с фактами `E-xxx`;
* при проверке на нашем бенчмарке (`metrics_model`) решает fact accuracy, hallucination rate,
  recall по проблемам и latency — эти цифры надо получить на **своём** наборе, а не брать из карточки;
* маленькая модель (8B) с нашим LoRA обычно обходит большую без дообучения на узкой
  инженерной задаче.

## 4. Три сценария развёртывания

| Сценарий | Машина клиента | Модель | Сеть | Плюсы / минусы |
|---|---|---|---|---|
| **A. Полностью локально (цель проекта)** | 16 ГБ RAM, CPU; опц. GPU 8 ГБ | Qwen3.5-9B Q4 (+LoRA) | не нужна | данные не покидают клиента; 5–15 ток/с на CPU, 30+ на GPU |
| **B. Гибрид** | то же | лёгкая модель локально (быстрые ответы на «что на экране»), тяжёлая — по запросу | только для сложных запросов, с согласия клиента | выше качество; нужен сетевой контур и разрешение на передачу данных |
| **C. Центральный сервер** (не наш сценарий) | тонкий клиент | модели от 35B-A3B и выше при 2×48 ГБ GPU | постоянная | максимум качества; но данные уходят с объекта и есть капзатраты |

Рекомендация: **A по умолчанию** (требование «у клиента на не самых мощных ПК»),
**C — как экспериментальная ветка** для сравнения качества и как генератор обучающих данных.

## 5. Как менять модель в проекте

1. Обучение: `python -m src.train.qlora_sft --train data/splits/train.jsonl` — модель, LoRA-параметры
   и режим берутся из `configs/model.yaml`; для другого чекпойнта добавить `--model <HF-id>`.
   План обучения печатается без GPU: `python -m src.train.qlora_sft --print-plan`.
2. Оценка: `python -m src.eval.metrics_model --pred ... --eval-set data/splits/eval_test.jsonl` —
   сравнение кандидатов **на одном и том же наборе** (Qwen3.5-9B, 4B как «слабый ПК», 35B-A3B).
3. Фиксация: результат в `outputs/<run>/run.json` (модель, хэш датасета, гиперпараметры, метрики).
4. Приёмочное правило MVP: кандидат допускается, если `fact_accuracy ≥ 0.95`,
   `hallucination_rate ≤ 0.05`, `latency p95 ≤ 8 с` и он не хуже текущего по recall проблем.

## 6. Минимальные требования к машине клиента (для варианта A)

| Компонент | Минимум | Комфорт |
|---|---|---|
| RAM | 16 ГБ | 32 ГБ |
| CPU | 4 ядра x86-64 (AVX2) | 8 ядер |
| GPU | не нужна | NVIDIA 8–12 ГБ (ускорение в 3–5 раз) |
| Диск | 10 ГБ | 25 ГБ (несколько моделей + логи) |
| ОС | Windows 10/11 x64 | то же |

Проверка на месте: `llama-bench`/`llama-cli` с нашей GGUF-сборкой + бенчмарк
`src/eval/metrics_model.py` на 20 кейсах — 10 минут работы.

## 7. Итог

* **Основная модель — Qwen3.5-9B** (Apache 2.0, ~5–6 ГБ в Q4): работает на клиентском ПК
  без GPU, длинный контекст, есть GGUF-сборки.
* **Резерв:** Qwen3.5-4B для самых слабых машин, Qwen3.5-35B-A3B для мощных.
* **AliceAI-80B-A3B отклонён** (05.10.2026): 80B весов + экспериментальный рантайм —
  это серверная история, а не клиентский ПК.
* Финальные цифры качества фиксируем **по нашему бенчмарку**
  (`data/splits/eval_test.jsonl`, `src/eval/metrics_model.py`), а не по карточкам моделей.

## 8. Сборка клиентской версии (GGUF)

```bash
# 1) обучить адаптер (GPU-машина)
python -m src.train.qlora_sft --train data/splits/train.jsonl --val data/splits/val.jsonl \
    --out outputs/qwen3.5-9b-epanet-v1

# 2) слить LoRA с базой и сконвертировать в GGUF (llama.cpp)
python llama.cpp/convert_hf_to_gguf.py outputs/qwen3.5-9b-epanet-v1 --outfile qwen35_9b_epanet_f16.gguf
llama-quantize qwen35_9b_epanet_f16.gguf qwen35_9b_epanet_Q4_K_M.gguf Q4_K_M   # ≈5.8 ГБ

# 3) запуск на клиенте (OpenAI-совместимый сервер, всё локально)
llama-server -m qwen35_9b_epanet_Q4_K_M.gguf -c 8192 -ngl 99 \
    --temp 0.2 --top-p 0.8 --top-k 20 --repeat-penalty 1.05 --host 127.0.0.1 --port 8080
```

Проверка на месте (10 минут): `python -m src.eval.metrics_model --pred data/eval/predictions.jsonl`
на 20 кейсах из `data/splits/eval_test.jsonl` — фиксируем latency, VRAM/RAM и fact accuracy
именно на этой машине.
