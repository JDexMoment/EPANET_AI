# Как получаются данные

## 1. Общая схема

```
data/raw/*.inp            configs/dataset.yaml                EPANET (PDA)          Analytics
   базовые сети  ─────▶  очередь неисправностей  ─────▶  расчёт 24 ч  ─────▶  KPI/алерты/evidence
                              (seed, fault_mix)          результаты            ─────▶ Context Builder
                                                                                      ─────▶ llm_context
                                                                                      ─────▶ кейсы для инженеров
```

## 2. Режим расчёта: PDA

По умолчанию используется **PDA** (Pressure Driven Analysis, EPANET 2.2+):
при давлении ниже требуемого подача честно снижается → в результатах появляется
**недоподача**, а не физически невозможный отрицательный напор.

```yaml
# configs/dataset.yaml
epanet:
  demand_model: PDA
  required_pressure_m: 20.0
  minimum_pressure_m: 0.0
  pressure_exponent: 0.5
```

Поэтому в аналитике есть отдельное правило `supply_deficit_*` («потребителю подано меньше
расчётного») — ключевой признак аварийного режима.

## 3. Типы сценариев (fault_mix)

| Тип | Что вносится | Диапазон | Метка | Ожидаемый эффект |
|---|---|---|---|---|
| `pipe_roughness_drop` | C трубы ↓ (зарастание) | ×0,35…0,75 | pipe_incrustation | рост потерь напора, падение давления за участком |
| `pipe_roughness_gain` | C ↑ (ошибка модели / гладкая труба) | ×1,30…1,60 | pipe_incrustation | заниженные потери, давление выше ожидаемого |
| `pipe_closed` | участок закрыт | — | pipe_closed_section | перераспределение потоков, перегрузка обходов |
| `demand_increase` | спрос узла × | ×1,5…4,0 | demand_anomaly | локальное падение давления, недоподача |
| `pump_degradation` | кривая насоса ↓ | ×0,70…0,90 | pump_degradation | падение давления по всей зоне подачи |
| `tank_level_low` | стартовый уровень = min | — | tank_level_deficit | потеря регулирующего запаса |

Дополнительно: случайный разброс базового спроса ±3 % (`demands_jitter_pct`) — чтобы кейсы
были не копиями друг друга.

Помимо неисправностей обязательно генерируется **базовый сценарий** той же сети
(`vn01__baseline`): он нужен и как эталон для сравнения, и как источник кейсов «проблемы нет».

## 4. Команды

```bash
# 1. Сценарии (30 с неисправностями + baseline) — ~3 с на демо-сети
python -m src.generate.run_scenarios --network vn01 --count 30

# 2. Аналитика + контексты по всем сценариям
python -m src.generate.build_derived_all

# 3. Кейсы для инженеров (вопросы + факты + пустой gold)
python -m src.dataset.build_cases

# 4. Партии и HTML-формы
python -m src.dataset.make_batches
python -m src.dataset.make_expert_pack --all
```

## 5. Как добавить свою сеть

1. Положить `.inp` в `data/raw/` (проверить, что EPANET считает без ошибок).
2. Зарегистрировать в `src/generate/run_scenarios.py`:
   ```python
   NETWORKS = {"vn01": "data/raw/sample_net_01.inp",
               "vn02": "data/raw/sample_net_02.inp"}
   ```
3. Проверить нормы для этой сети (давление/скорости/уровни) и при необходимости
   завести отдельный `configs/thresholds_vn02.yaml` (передаётся параметром в `build_derived`).
4. Сгенерировать сценарии и сверить распределение алертов:
   ```bash
   python -m src.generate.run_scenarios --network vn02 --count 40
   ```

Рекомендация по датасету: 3–5 разных сетей (разные размеры, тупиковые/кольцевые, с башней
и без, с одной/двумя насосными станциями) — это резко снижает переобучение модели на конкретную сеть.

## 6. Как добавить свой тип неисправности

1. Дописать спецификацию в `FAULT_SPECS` (`src/generate/run_scenarios.py`): цель, диапазон
   масштаба, метка из `configs/labels.yaml`, ожидаемый эффект.
2. Реализовать применение правки в `_apply_edit()`.
3. Добавить вес в `fault_mix` (`configs/dataset.yaml`).
4. Если нужен новый порог — добавить правило в `configs/thresholds.yaml` и в `detect_alerts()`
   (например, «перелив резервуара», «насос работает с рециркуляцией», «нулевое потребление в узле»).

## 7. Наблюдаемость эффекта (важно для качества меток)

В `derived_metrics.json` пишется блок `observability`:

```json
{"worst_delta_min_pressure_m": 0.71, "nodes_worse": 3, "visible_effect": true,
 "note": "эффект слабый — внимательно проверьте, есть ли инженерная проблема"}
```

Слабый эффект — это **не брак**: такие сценарии дают кейсы «изменения есть, но инженерной
проблемы нет / недостаточно данных», которые защищают модель от выдумывания аварий.
Но доля таких сценариев должна быть ≤ 25 %, иначе датасет перекошен (см. `metrics_offline`).

## 8. Воспроизводимость

- `seed` — в `configs/dataset.yaml`; каждый сценарий получает `seed + i`.
- Сценарий не пересчитывается, если его `scenario_id` уже есть в `data/scenarios/manifest.jsonl`.
- Полный пересчёт: удалить `data/scenarios/` и запустить конвейер заново.
- На больших сетях результаты держать в Parquet и хранить не всё сутки, а «окно ±2 ч от пика»
  (в `configs/dataset.yaml` предусмотреть `results.format: parquet`, `keep_hours`).
